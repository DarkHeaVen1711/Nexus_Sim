Nexus_Sim → "Nexus Twin": Master Plan + Repo Audit

Basis: the attached repo dump (README, PROGRESS_REPORT, docs, engine, pipeline, ml, dashboard source). I could not run the code or see the live GitHub state, so every finding is labelled:

  • [V] = verified by reading the code in the dump
  • [?] = strong signal, but needs a quick check on your side (a command is given)

Part 1. Repo audit

1.1 What is genuinely good (keep it)

  • The sidecar architecture (C++ engine + Python services + event bus) is clean and gives you real integration seams.
  • The SoA agent layout, quadtree, thread-pool tick, SPSC-ring ONNX inference path and the latency histogram are solid engineering.
  • The signal-policy abstraction (Webster / fuzzy / Type-2 / RL) is exactly the right shape for a "compare policies" platform.
  • Test coverage exists across engine, pipeline and ML.

The problems below are mostly not architecture problems. They are modelling-validity, sampling and claims-integrity problems, and they matter because the next stage (I*, OSM upload, blended AI) will inherit them.

1.2 Critical: the simulation does not model what the docs say it models

ID Finding Evidence Fix
E1 [V] Oncoming and crossing vehicles become "leaders." find_leader accepts any active agent that is ahead along my heading (proj > 0.5) and within 5 m sideways. It never checks edge, direction, or route. Both directions of a road use the same centreline (no lateral offset), so an oncoming car on the reverse edge qualifies as a leader. IDM then brakes for it. Simulation.h::find_leader, compute_world Restrict leaders to same directed edge (or next edge on own path); use lateral offset per direction; compute net gap (centre distance − leader length), not centre-to-centre.
E2 [V] lane and chaos have no effect on traffic dynamics. lane is never used by compute_world, find_leader or the broadcast. lane_discipline only feeds a lane-change probability that changes the unused lane field. chaos does not alter any IDM parameter. So the GA "chaos" gene, the --chaos flag, the Ahmedabad chaos: 0.4 setting and the chaos sensitivity sweep cannot move any engine metric. IDM.h, Simulation.h::maybe_lane_change Make lateral position physical (this is I*-Drive, Part 5). Until then, remove chaos from calibration chromosomes and stop presenting it as a result.
E3 [V] Wrong modal split from a sampling bug. spawn_agents and respawn_arrived call select_agent_type_for_road(get_num_lanes(start, end), ...) where start/end are two random nodes. get_num_lanes looks for an edge start→end, almost never finds one, and returns the default 1. The type sampler then takes the "narrow residential" branch: ~45% pedestrians, 30% two-wheelers, 15% autos, 10% cars, in every city, Chicago included. Pedestrians are routed over the road graph with IDM and counted in avg_speed. Simulation.h, IDM.h::select_agent_type_for_road Per-city modal split in cities.yaml (or per zone × hour). Sample type independently of the OD pair. Move pedestrians to a separate layer or exclude them from vehicle metrics.
E4 [V] OD-driven spawning is 100% cars, lane 0. spawn_od_agent hard-codes AgentType::Car. In OD mode (Chicago and any city with an OD file) no buses, autos or two-wheelers ever appear. Simulation.h::spawn_od_agent Same modal-split sampler as E3.
E5 [V] Unbounded agent growth in OD mode. Every OD spawn calls add_agent. Arrived agents are never recycled, and failed-route agents are added as Arrived. tick(), collect_wait_counts(), compute_zone_metrics() and broadcast_state() all loop over every agent ever created. Cost per tick grows with wall-clock time. Simulation.h::spawn_od_agent, all whole-array loops Free-list slot reuse or periodic compaction; keep an active-index list.
E6 [V] Startup is O(V×E). init_signals scans all edges twice per node. On Chicago (29,733 nodes × 54,210 edges × 2) that is roughly 3×10⁹ comparisons before the first tick. Simulation.h::init_signals Build a reverse adjacency once (O(E)).
E7 [V] Signal phases and the Webster baseline are not physically grounded. Incoming edges are sorted by angle and split in half, which puts perpendicular approaches in the same phase and separates opposing ones. Phase volumes are constants (200 + 30 × degree), not measured flow. Nodes with degree ≥ 7 get signals even without a traffic_signals tag. The "RL vs Webster" comparison therefore uses a baseline fed made-up volumes. Simulation.h::init_signals Pair opposing approaches (angle mod 180°); derive volumes from a warm-up run or OD; add stronger baselines (max-pressure, actuated, SOTL).
E8 [V] edge_key overflows and collides. (u * 0x9e3779b9) ^ v on int64_t. With OSM node ids around 10¹⁰ the multiply exceeds int64 (undefined behaviour), and the XOR key is not collision-free, so one edge can be blocked, tolled or bus-laned by accident. Pathfinder.h::RoutingPolicy::edge_key Remap node ids to dense 0..N-1 at load; key edges by edge index or pair<int,int>. This also lets A* use flat arrays instead of unordered_map.
E9 [V] Poor RNG sampling in lane change. maybe_lane_change constructs std::mt19937 rng(id + tick_count_) per agent per tick. That is 20,000 × 624-word state initialisations per tick, and the seeds are consecutive integers, so the first draws across neighbouring agents are correlated. Simulation.h::maybe_lane_change Per-agent PCG32/xoroshiro state in the SoA, or a splitmix64 hash of (seed, id, tick).
E10 [V] Stochastic routing draws fresh noise on every edge relaxation. In compute_path_stochastic, noise(rng) is called each time an edge is relaxed, so the same edge gets different costs inside one search. Lognormal noise with median 1 can also make an edge cheaper than its Euclidean length, which makes the A* heuristic inadmissible. Route diversity is real, but the cost model behind it is inconsistent. Pathfinder.h Fixed per-agent, per-edge perturbation (hash of agent_id, edge_id), or a per-agent perceived-cost multiplier (this becomes I*-Route).
E11 [V] Wait-time and equity metrics are narrower than their names. wait_time accrues only when an agent is stopped within 5 m of a red signal. Queueing behind vehicles, unsignalised delay and incident delay are not counted. Gini is computed over per-zone means of currently active agents only (survivorship bias), and zones in fetch_graphs.py are latitude bands, so "equity" measures north–south stripes. Simulation.h::compute_zone_metrics, fetch_graphs.py Total delay = journey time − free-flow time, per agent, including finished agents; zones from admin boundaries or a real partition; Gini over agents or population-weighted zones.
E12 [V] Broadcast payload includes each agent's full path every frame. A FlatBuffers schema (agent_delta.fbs) exists but the live path is hand-built JSON. Bandwidth and string building scale with agents × path length × FPS. Simulation.h::broadcast_state Send paths once (or on selection), then only deltas; use the existing FlatBuffers schema.
E13 [V] Silent fallback to a synthetic grid. fetch_graphs.py generates a 12×12 grid if Overpass fails or returns < 10 elements, and writes it as graph.json with nothing marking it synthetic. Also: oneway handles only "yes", not -1, true, 1, or roundabouts; the highway regex omits unclassified, service and living_street, which matter a lot for Indian cities; lanes="2;3" silently becomes 1. Paris and Ahmedabad graphs are small (90 and 75 nodes) for their bounding boxes. pipeline/fetch_graphs.py Add provenance (osm / synthetic / subset), fail loudly, fix tag parsing. [?] Check data/*/graph.json provenance.

1.4 Critical: soft computing, CV and NLP claims

ID Finding Fix
S1 [V] NSGA-II runs on a closed-form toy function, not the simulator. f1_wait = 25 + 15(1−α) + 5·chaos; f2_gini = 0.20 + 0.25(1−β) + 0.05(1−sf). The two objectives depend on disjoint variables (α,chaos vs β,sf), so a single point (α, β, sf all maximal) dominates everything. The Pareto front is one point, not a trade-off. The code also has no crowding distance, no crossover, and only ever fills from the first front. It is a mutation-only non-dominated filter, not NSGA-II. Evaluate objectives through the engine (with a surrogate to cut cost), use real NSGA-II (or pymoo), and pick objectives that genuinely conflict.
S2 [V] Global np.random everywhere in ANFIS, ABC, GP, ACS and NSGA-II. No injected RNG, so results are irreproducible and seeds can't be paired for A/B. Inject numpy.random.Generator everywhere.
S3 [V] Virtual-camera "accuracy" is count agreement: 100 − error_pct on detected count vs ground-truth count. False positives cancel false negatives, so this is not detection accuracy. Report precision/recall/F1 (IoU-matched), MOTA/IDF1 for tracking.
S4 [V] ACS exists only in Python (ml/sc/ant_colony.py). Its docstring says SC-5 while the table says SC-6, and I found no pheromone weights in the engine's Pathfinder. The "−18.4% detour latency" is therefore not an engine result. NSGA-II is labelled SC-10 in code, SC-12 in the table. Integrate into the engine (Pillar 3) or relabel as offline.
S5 [?] NLP accuracies (98.2%, 96.0%, …) have no evaluation set in the dump. I found no labelled test data for NLP-1…12. Build the gold sets (Pillar 4).

Part 2. The unifying idea

2.1 One project, four directions

Nexus Twin: a city-agnostic, closed-loop digital twin for mixed, weakly lane-disciplined traffic (the Indian case, and the general case), that perceives → understands → adapts → acts → explains.

Each pillar owns one verb, and none can be removed without breaking the loop:

Pillar Verb Owns Cannot be removed because…
CV Perceive The twin's senses. Turns pixels (virtual cameras now, real footage later) into state estimates with uncertainty, and into behaviour parameters. Without it, RL has only ground truth, which is unrealistic, and SC has nothing to calibrate against.
NLP Understand and explain The twin's language. Turns human text (multilingual) into structured scenarios, incidents and objectives, and turns decisions into explanations. Without it, objectives and incident reports can't enter the loop, and decisions are opaque.
SC Adapt and govern The twin's uncertainty handling. Fuzzy reasoning, calibration, multi-objective trade-offs, safe arbitration, swarm routing. Without it, the system can't calibrate to a new city, can't handle vagueness, and RL has no safety net.
RL Act The twin's control. Signal control and learned vehicle behaviour. Without it, the loop only observes.

2.2 The spine: a shared Belief State

The pillars talk through one typed Belief State, not through point-to-point hacks. Your existing event bus (port 9005) becomes its transport.

2.3 The substrate every pillar stands on

Two pieces of infrastructure make it a single system rather than four:

  1. City Onboarding Pipeline (your OSM importer, generalised). Upload OSM → Graph v2 → CV road-attribute inference → SC calibration → NLP gazetteer → RL warm-start. Every pillar has a step in it, and "time to a working twin for an unseen city" becomes a headline metric.
  2. I* (Indian-behaviour model). It is the behavioural "physics" that CV measures, SC calibrates, NLP describes and RL must cope with. It is the place where all four pillars touch the same object.

Part 3. Four pillar-projects (each publishable alone)

Each has a research question, scope, milestones, standalone deliverable, metrics, and its hooks into the others.

Pillar 1: RL. "Learning control for mixed traffic under partial observability and behavioural shift"

Research question: Can a city-size-agnostic learned controller beat strong classical baselines in heavy-tailed, non-lane-based traffic when it sees only camera-derived, noisy observations?

Scope

  • 1A. Engine-in-the-loop environment. Expose the C++ engine as a vectorised, deterministic, headless Gym/PettingZoo env (pybind11 or shared-memory/ZeroMQ). Retire the Python surrogate for headline results. This fixes R1/R2 and is the prerequisite for everything else.
  • 1B. Real MAPPO / GNN-MAPPO. Centralised critic; a graph-attention encoder over the road graph so one policy handles any topology and phase count (drops the fixed "4 approaches, 2 phases" limit). This is what makes "upload any city" real for RL.
  • 1C. Constrained RL for equity. Treat Gini/max-zone-delay as a constraint (Lagrangian/CMDP) instead of a weighted reward term; report the constraint-satisfaction curve.
  • 1D. Robustness. Domain randomisation over I* behaviour profiles and sensor noise; evaluate zero-shot on held-out cities and held-out behaviour profiles.
  • 1E. Vehicle-level policies (stretch). SAC/TD3 (currently "showcase") learn micro-behaviour by imitation of CV-extracted trajectories, then RL-refine; DDPG/TD3/SAC finally earn a deployed role.
  • Baselines: Webster (with real volumes), max-pressure, actuated/SOTL, fuzzy, Type-2 fuzzy, and the current IPPO as an ablation.

Standalone deliverable: "GNN-MAPPO for signal control in mixed traffic": engine-based results, zero-shot transfer table, equity-constrained variant.

Metrics: mean delay, throughput, p95 delay, Gini (agent-level), stops per vehicle, zero-shot delay vs Webster/max-pressure on held-out cities, decision latency (keep < 1 ms p95).

Cross-pillar hooks: consumes edge_state (CV) and objective (NLP); its arbiter and warm-start come from SC; emits decision_log for NLP.

Pillar 2: CV. "Vision-based state estimation and behaviour identification in unstructured traffic"

Research question: From overhead/roadside video of non-lane-based traffic, can we recover (a) per-approach traffic state and (b) driver-behaviour parameters accurately enough to drive a controller and calibrate a simulator?

Scope

  • 2A. Honest detection/tracking stack. Extend the virtual camera to render two-wheelers, autos, buses and pedestrians with realistic occlusion, night/rain/glare augmentation and camera-placement randomisation. Report IoU-matched precision/recall/F1 and MOTA/IDF1 for CV-3/4/11. Add a small real validation clip set (public Indian-traffic datasets or your own footage).
  • 2B. Traffic-state estimator. A network that maps frames (+ optical flow) to per-approach queue, density and speed with uncertainty (deep ensemble or MC-dropout). This is the object RL consumes in the camera-only regime.
  • 2C. Behaviour identification. From tracked trajectories, extract headway, lateral-gap distribution, filtering rate, hard-braking rate; fit I* parameters. This is the CV→SC calibration channel.
  • 2D. Road-attribute inference for OSM onboarding. From tiles/satellite imagery and OSM tags, estimate lanes, effective width and one-way status where tags are missing (fixes E13's lanes default). Use U-Net (CV-5) and Hough (lane detector).
  • 2E. Anomaly/blockage detection with calibrated false-alarm rates (CV-7/9), producing incidents[] candidates for fusion.
  • Attention interface: accepts "look at region X" from NLP to change ROI/priority (active perception).

Standalone deliverable: "Camera-grounded traffic state and behaviour estimation for non-lane-based traffic", with a synthetic benchmark and a small real validation set.

Metrics: detection mAP@0.5 (synthetic and real), MOTA/IDF1, state-estimation MAE (queue length, speed), calibration error (ECE) of uncertainty, behaviour-parameter recovery error (relative error vs known I* ground truth), road-attribute accuracy.

Cross-pillar hooks: feeds edge_state and incidents (with σ), supplies behaviour_profile estimates to SC, receives ROI requests from NLP.

Pillar 3: Soft Computing. "Uncertainty-aware calibration, arbitration and multi-objective governance of a traffic twin"

Research question: How do you calibrate and govern a heterogeneous-traffic simulator and its learned controllers under vagueness, noisy sensing and conflicting objectives, cheaply and safely?

Scope

  • 3A. Surrogate-assisted multi-objective calibration. CMA-ES/NSGA-II over [speed_factor, route_spread, modal split, I\* parameters, demand scale] against real data where it exists (Chicago) and stylised facts where it doesn't (headway distribution, capacity drop, two-wheeler percolation, speed-flow curve). An ANFIS or GP surrogate cuts engine evaluations; use Sobol/Latin-hypercube sampling for the initial design.
  • 3B. Fuzzy driver model. A Type-2 fuzzy "aggression" inference (inputs: gap, relative speed, vehicle type, time pressure → aggression, honk propensity, gap-acceptance) inside I*-Drive, so fuzziness is in the physics, not just the signals.
  • 3C. Fuzzy arbiter / safety shield. Watches RL confidence (entropy), CV uncertainty and incident severity, and blends or falls back between MAPPO, fuzzy and max-pressure. Directly addresses the cities where RL currently loses to Webster.
  • 3D. Swarm routing in the engine. Port ACS/ABC into C++ as a decaying per-edge pheromone/congestion field that I*-Route reads; also rendered as a CV-style heat layer.
  • 3E. Interpretability. Rough-set feature reduction on observations; ANFIS/GP distil the RL policy into readable rules that NLP verbalises.
  • 3F. Real NSGA-II Pareto governance (fixes S1): engine-evaluated objectives (delay, Gini, emissions, safety proxy) whose front is presented to the user, with NLP-chosen preference (Pillar 4).

Standalone deliverable: "Surrogate-assisted multi-objective calibration and fuzzy arbitration for mixed-traffic digital twins."

Metrics: calibration error vs held-out data/stylised facts, evaluations-to-target (efficiency vs plain CMA-ES), hypervolume of the Pareto front, arbiter regret vs the best fixed policy, fallback correctness under injected faults.

Cross-pillar hooks: takes CV behaviour estimates and uncertainty; outputs calibrated behaviour_profile, fused incidents.severity, the arbiter, RL warm-starts and Pareto sets.

Pillar 4: NLP. "Language as the control and explanation interface for a traffic digital twin"

Research question: Can free-form, multilingual (English/Hindi/Gujarati/Hinglish) text be grounded reliably into executable simulation scenarios and objectives, and can control decisions be explained faithfully in language?

Scope

  • 4A. Scenario DSL + semantic parser. A validated JSON schema for closures, incidents, events, policy toggles, objectives and constraints. Parse text → DSL with confidence, schema validation, and clarifying questions on ambiguity. Regex/Naive-Bayes as fast paths; an LLM/seq2seq parser for the long tail; both scored on the same gold set.
  • 4B. Multilingual, code-mixed grounding. Transliteration-tolerant gazetteer built automatically from the imported OSM graph (street names in Latin/Devanagari/Gujarati script, fuzzy matching). Ahmedabad is your natural test bed.
  • 4C. Evidence fusion inputs. Extract incident events (type, place, time, severity cue) from text, and emit them as evidence for SC's fusion with CV.
  • 4D. Explanation generation. Turn decision_log entries and distilled rules (from 3E) into faithful explanations ("held green on Ashram Rd because the northbound queue exceeded the fuzzy 'long' threshold"). Faithfulness is tested, not asserted (perturb the cited feature and check the decision changes).
  • 4E. Objective elicitation. "Protect school zones 8–9 am, avoid gridlock" → weights and constraints → NSGA-II preference → RL constraint.
  • 4F. Knowledge graph of city entities/events with temporal queries; QA over it.
  • 4G. Gold datasets. Build and release a small annotated set (scenario commands, incident reports, explanation-quality ratings) so the NLP accuracy numbers become real (fixes S5).

Standalone deliverable: "Grounded multilingual scenario authoring and faithful explanation for traffic digital twins", plus a dataset.

Metrics: command→DSL exact-match and execution-match accuracy, slot-level F1 (place/time/type), geocoding accuracy on transliterated names, clarification precision, explanation faithfulness score, human-rated usefulness.

Cross-pillar hooks: writes incidents evidence and objective, issues ROI requests to CV, reads decision_log from RL and rules from SC.

Part 4. Proof that it is one system: ablation matrix and flagship scenarios

The rule: every pillar must have a measurable effect on the others. If removing a pillar changes nothing, that pillar isn't blended.

4.1 Flagship scenarios

NLP grounds the place → CV confirms/denies → SC fuses into fuzzy severity → engine blocks/slows edges → RL re-times signals, I*-Route reroutes → NLP explains and asks a clarifying question if evidence conflicts.

Part 5. OSM importer and I* (updated after the audit)

5.1 OSM importer: concrete spec

  • Input: .osm / .osm.pbf / GeoJSON upload, or bbox/place name (Overpass, rate-limited).
  • Stages (each a logged, sandboxed background job): parse (streaming parser, size and bbox caps) → filter road classes (include unclassified, service, living_street, *_link) → correct oneway (yes/true/1/-1, roundabouts, motorways) → parse lanes, maxspeed, width, name, highway, surface → largest strongly connected component → dense id remap → zones (admin boundary, else k-means/grid) → signals/crossings → OD proxy from building footprints → Graph v2 with provenance and a validation report.
  • Graph v2 edge: {u, v, length_m, lanes, width_m, speed_kmh, road_class, name, oneway, geometry}. The engine then needs an edge index per agent, per-edge speed limits and per-class behaviour.
  • Engine side: either a per-session engine process (own port) or a load_graph control message with hot reload. Add a graph-size guard tied to the agent budget.
  • Honest labelling: uploaded cities carry demand: modelled, not measured and an RL confidence badge; no MAPE claims.
  • Compliance: ODbL attribution; be polite to Overpass (file upload avoids it).

5.3 I*: two layers, one name

  • I*-Route (strategic): A* over perceived cost, not distance. Cost = f(free-flow time by road class, live congestion from the pheromone field, signal-delay aversion, familiarity bias to arterial roads, vehicle-type shortcut permissions). Weighted heuristic on purpose (satisficing), fixed per-agent perturbation (replaces E10's noise). Two-wheelers and autos may use narrow lanes; buses may not.
  • I*-Drive (tactical): modified IDM + lateral dynamics:
    • continuous lateral_offset in the SoA and physical lateral position in compute_world (this is what finally gives chaos/lane_discipline an effect, fixing E2, and it also fixes E1's direction/lateral confusion);
    • filtering through gaps by narrow vehicles (reuse the quadtree lateral query);
    • Type-2 fuzzy aggression → gap acceptance, following distance and horn propensity (Pillar 3B);
    • honk events with a mild yield effect and a per-edge honk-density metric;
    • Poisson-triggered, heavy-tailed hard braking (creates shockwaves, an ideal stress test for RL).
  • Per-city behaviour profile in cities.yaml (generalising chaos), with CV-estimated and SC-calibrated parameters.
  • Validation is by stylised facts (no measured Ahmedabad OD exists): headway distribution, lateral-gap distribution, capacity vs lane-discipline, two-wheeler percolation, speed–flow curve.
  • Performance guardrails: O(k) neighbour work per agent, per-agent RNG, and a 20k-agent, 60 FPS regression test in CI before I*-Drive is allowed on by default (flag it initially).

Part 6. Evaluation and sampling protocol (applies to every result)

  1. Seeds and pairing: ≥ 30 seeds per configuration; common random numbers across compared policies (same demand and behaviour draws) so A/B differences are paired.
  2. Warm-up and horizon: discard the first 300–600 s of sim time; run ≥ 1 h of sim time for delay metrics.
  3. Design of experiments: Sobol/Latin-hypercube for parameter sweeps; never a hand-picked grid of 4.
  4. Splits: calibrate on one time window / OD subset, validate on another; hold out at least one whole city for transfer claims; never tune on evaluation seeds.
  5. Statistics: bootstrap 95% CIs, effect sizes, and multiple-comparison correction for the algorithm tables.
  6. Reproducibility: every reported number is generated by a script from raw logs; each run records git SHA, config hash, seed set.
  7. Metrics v2: total delay per agent (journey time − free-flow time, including finished agents), throughput, p95 delay, stops, agent-level Gini plus per-zone max delay, emissions, and a safety proxy (hard-brake and time-to-collision counts).
  8. Baselines: Webster with real volumes, max-pressure, actuated, fuzzy, Type-2 fuzzy, IPPO (current), GNN-MAPPO (new).
  9. CI gates: parity tests (train vs deploy observation), determinism test, 20k-agent FPS budget, and a "no untracked numbers in README" check.

Risk Mitigation
Stage 0 may lower headline numbers (e.g. the +26.3% may shrink or disappear on the engine). Treat it as a research finding. Honest negative/positive results with CIs are stronger than a surrogate win.
I*-Drive can break the 60 FPS / 20k-agent budget. Flag-gated; per-agent O(k) logic; CI perf gate.
Real Indian traffic footage/data may be hard to get. Start with synthetic + stylised facts; add a small real clip set for validation only.
Scope: four standalone-sized projects. Ownership per pillar, shared substrate, strict Stage gates; cut stretch items (1E, real-footage validation) first.
LLM dependence in NLP. Keep the regex/NB fast path; the LLM is a fallback scored on the same gold set.
